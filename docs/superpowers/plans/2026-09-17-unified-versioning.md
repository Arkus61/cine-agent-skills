# Unified Versioning Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Привести Cine Agent Skills к одной общей версии системы, контрактов и набора скиллов, убрав разделение рабочего процесса на поколения 0.1 / 1.0 / 2.0.

**Architecture:** Одна вручную изменяемая версия в `pyproject.toml`; остальные значения синхронизируются и проверяются автоматически. Различия между уровнями полноты пакета сохраняются как функциональные профили без номеров поколений. Старые данные переводятся в актуальный контракт отдельной утилитой, а не отдельными постоянными ветками валидатора.

**Tech Stack:** Python 3.11+, pytest, JSON Schema Draft 2020-12, JSON, YAML, Markdown, Make, GitHub Actions. Без новых платных сервисов и сетевых зависимостей исполнения.

**Spec:** Утверждённая целевая модель перенесена в `docs/superpowers/specs/2026-09-17-unified-versioning-design.md`; этот файл остаётся пошаговым журналом исполнения.

**Status:** В работе на `feature/film-os-modernization`, 18 сентября 2026 года. Пользователь зафиксировал название общей дорелизной версии: `0.3`, техническая запись — `0.3.0`. Синхронизация, нейтральные профили, активные схемы/шаблоны/evals/examples, CLI-отчёты, переименование примеров и безопасная миграция legacy-пакетов реализованы и покрыты focused-тестами. Полный workflow на LangGraph, стандартный MCP-клиент, живой Blender-пилот и измерительная eval-серия остаются открытыми; текущая ветка не заявляет их готовыми.

## Целевая модель

### Одна версия системы

Номер перехода по решению пользователя — **0.3**, техническая запись во всех машинных полях — `0.3.0`. Проект ещё не достиг первого стабильного релиза; прежние обозначения `0.1`, `1.0` и `2.0` относятся к истории разработки, а не к трём стабильным выпускам продукта. Изменение контрактов на этом этапе не является основанием объявлять версию `3.x`. После перехода остаётся одна активная дорелизная версия, а не ещё один параллельный рабочий режим. Уже опубликованный snapshot с метаданными `2.0.0` и его commit сохраняются как история; их нельзя переписывать задним числом.

Переход от прежних метаданных `2.0.0` к `0.3.0` — осознанное исправление дорелизной нумерации. Утилита миграции должна распознавать его по явной таблице исходных контрактов, а не по правилу «целевой номер больше исходного». Для уже установленного пакета с прежним номером инструкция должна предусматривать явную установку новой сборки и проверку `--version`, а не рассчитывать на автоматическое обновление до численно меньшей версии.

Единственный редактируемый источник — `[project].version` в `pyproject.toml`. Не создавать вторую независимую версию в `VERSION`, отдельные счётчики скиллов или нумерованные копии каталогов.

| Место | После перехода |
|---|---|
| Версия пакета и `cine_skills.__version__` | `0.3.0` |
| `schema_version` актуальных артефактов | `"0.3.0"` |
| `release_version` манифестов | `"0.3.0"` |
| `artifacts[].schema_version` манифестов | `"0.3.0"` |
| Верхнеуровневый `version` существующих eval-наборов | `"0.3.0"` |
| `system-manifest.json` | Одна `release_version` для полного списка из 37 скиллов |
| JSON-отчёты валидатора | `system_version: "0.3.0"` плюс функциональный профиль |
| Архив | Имя вычисляется из общей версии, без вручную вписанного номера |

Названия полей `schema_version` и `release_version` пока сохраняются: они указывают назначение значения, но больше не имеют независимых счётчиков. Не добавлять одинаковый номер в каждый Markdown-файл или во frontmatter скилла. Каждый файл входит в один выпуск через общий манифест и Git-коммит.

Обновление будущего номера выполняется общей синхронизацией. Сохранённые пользовательские проекты не переписываются при установке новой версии. Даже если следующий переход меняет только метаданные, он должен быть описан как проверенная миграция, а не молчаливое принятие любой версии.

### Функциональные профили вместо поколений

| Сейчас | Актуальный профиль | Что сохраняется |
|---|---|---|
| `core-v0.1` | `scene-core` | Базовый набор сценовых артефактов |
| `full-v1` | `scene-full` | Полный сценовый пакет и его проверки |
| `story-v2` | `story` | История и сценарные единицы |
| `production-v2` | `production` | Подготовка производства |
| `post-v2` | `post` | Планирование постпроизводства |
| `full-creative-v2` | `full-creative` | Проект целиком |
| `auto` | `auto` | Выбор полноты сценового пакета по наличию манифеста |

`scene-core` и `scene-full` используют одни актуальные схемы, отличаются только составом и полнотой проверок. Сохранение базового режима не означает сохранение старой версии. Отдельные специалисты и слои остаются независимо применимыми.

Активный CLI не поддерживает скрытые алиасы прежних поколений. Старый флаг даёт код 2 с указанием нового имени; старый формат данных — код 1 с сообщением о необходимой миграции. Текущая валидация никогда не изменяет входные файлы.

### Область изменений и исключения

Меняем только версии системы, профили, ссылки на них, текущие примеры и управляющую документацию. Сохраняем разные схемы для разных типов артефактов: единая версия не означает одну огромную универсальную схему.

Не изменяем версии Python, библиотек, GitHub Actions, JSON Schema, Apache-2.0, даты источников, номера редакций сценария или медиа (`draft_version`, `edit_version`, `r2` и аналогичные поля). Не переименовываем ID сцен, кадров, персонажей и других сущностей. Не меняем художественное содержание.

Исторические спецификации, логи, исходные forward-отчёты и changelog сохраняют свои настоящие номера. Вводится явный список архивных материалов: агент не должен брать их за актуальную инструкцию. Нельзя объявить все `docs/**` архивом — текущие руководства должны проверяться.

## Рассмотренные способы

1. **Единый контракт и единый выпуск — рекомендуется.** Убирает расхождение чисел во всех активных слоях; требует согласованной миграции и регрессии.
2. **Только переименовать профили.** Дешевле, но `1.0` и `2.0` останутся внутри JSON и шаблонов; задачу полностью не решает.
3. **Начать новую реализацию с нуля.** Даёт чистую структуру, но неоправданно рискует уже работающими 37 скиллами и проверками. В этот план не входит.

## Global Constraints

- Одна выбранная активная дорелизная версия: `0.3` (технически `0.3.0`); один редактируемый источник: `pyproject.toml`.
- Сохранить 37 имён скиллов, 35 предметных JSON-схем, текущие ID, семь форматов и четыре производственных режима.
- Сохранить правила работы без платного API и без сети во время валидации.
- Сохранить коды выхода 0/1/2, детерминированные диагностики и schema-first проверки.
- Не ослаблять ссылки, покрытие кадров, проверку фактов, согласований или доказательств ради зелёных тестов.
- Сохранить различия `valid`, `planned`, `awaiting-media`, творческого одобрения и готовности медиа.
- Скиллы остаются в `.agents/skills`; frontmatter содержит только `name` и `description`.
- Репозиторные инструкции и новые файлы реализации писать на английском; этот пользовательский план — на русском.
- `uv.lock` и чужие изменения не затрагивать.
- Не реализовывать Blender, генерацию медиа, Context Engine, базу данных или новый интерфейс.
- Не публиковать, не сливать PR и не переписывать удалённую историю без отдельного поручения.

## Порядок исполнения

Подготовка: задачи 1–3. Затем задачи 4–9 образуют согласованный переход контрактов. Их небольшие шаги проверяются по месту, но промежуточные состояния не объявляются готовым выпуском и не сливаются отдельно, пока полный набор проверок не зелёный. Задачи 10–12 закрывают защиту, документацию и выпуск.

Каждая нумерованная задача имеет свой критерий приёмки. После неё фиксировать результат проверки и небольшой коммит с конкретным списком файлов. Если задача остаётся красной, она остаётся незавершённой; нельзя просто заменить ожидания тестов или убрать проверку.

## Критерий завершения всей работы

Работа завершена, когда одновременно выполнены следующие условия:

1. В текущей системе одна версия, задаваемая в одном месте.
2. Все 37 скиллов входят в один выпуск; все 35 предметных схем согласованы с ним.
3. Нет активных профилей, папок примеров или инструкций, требующих выбрать 0.1, 1.0 или 2.0.
4. Функциональная полнота сценового пакета, независимые слои и все прежние предметные проверки сохранены.
5. Старые данные можно безопасно перенести без переписывания исходника и без выдумывания недостающих сведений.
6. Исторические материалы узнаваемы и не выданы за текущие результаты.
7. Проверки расхождения версий включены в обязательный CI; полный регрессионный набор и чистый архив проходят проверку.
8. Нет неоговорённых изменений в Blender, медиа-генерации, Context Engine или иных будущих подсистемах.
